# 未認識リスク同定PoCのソフトウェア・画面設計

## 1. 最小構成で何を確かめるか

最初のPoCは、研究者が場面とスタッフの既知情報を選び、**同じ判断設定で計算した危険内容のうち、既知事実だけでは確定できないものを、その根拠とともに確認する道具**とする。React画面は結果確認を助ける。対話生成や通知の最適化は初期機能に含めない。

本書は[REQ-008 revision2](../requests/2026-10-31-002-REQ-008-PoC.md)のR-04に対する設計提案である。[数理設計006](2026-10-31-006-REQ-008-identification-model.md)を処理の基準、[シナリオ・評価設計007](2026-10-31-007-REQ-008-scenarios-and-evaluation.md)を検証条件とする。今回は設計文書と画面例までであり、以下のモジュール、API、JSONファイルは未実装である。

| 初期PoCに含める | 今回の対象外 |
| --- | --- |
| 少数の模擬場面、固定した判断設定、AI仮想スタッフの既知情報の読込 | 実病棟の監視、実患者データの取込、臨床上の安全性の実証 |
| 有限の状態一覧と既知事実の照合、既存モデルによる評価、未確定内容と代替状態の出力 | 現実の全状態の網羅、未知を0とする穴埋め、人の認識の自動推定 |
| 同じ情報を渡した比較法、研究者による結果・根拠・設定の確認 | 危険順位の一致、将来事故予測、最小通知数、対話の良し悪しの最適化 |
| 実スタッフ評価へ切り替えられる入力・表示の分離 | 今回の実スタッフ評価の実施、既存危険度計算の変更 |

## 2. 入出力とデータの分け方

### 2.1 保存単位と型

一つの場面に患者・物体・スタッフをまとめて保存する。患者ごとに物体やスタッフ位置を独立に変更すると、共有空間として矛盾するためである。`FeatureFrame`は、その場面から既存の変換処理で作る患者別の計算入力であり、スタッフの知識ではない。

| 文書内の型名 | 保存する内容と制約 |
| --- | --- |
| `SceneState` | `state_id`、患者・物体・スタッフの配列。座標・姿勢等は有限数値、IDは一意。既存ScenarioLoader向けの具体形式へ変換する |
| `StateLibrary` | `library_version`と`SceneState[]`。有限状態一覧L。現在状態x*を含む。全患者の共有配置を維持する |
| `ThetaBundle` | 個別AHP/Fuzzy設定と下位変換・集約方式、モデル版、正規化した設定のハッシュ。全状態・比較法で同一とする |
| `KnowledgeProfile` | 対象スタッフID、時刻、既知事実KF、関係KE、具体的危険内容KR、来歴。対象スタッフは物理的に最寄りのスタッフとは別に指定する |
| `EventDefinition` | 事象ID、患者、種類、参照計算項目、成立条件、重要性条件、定義版。一件の事象とは成立・不成立を判定できる危険内容を指す |
| `RunResult` | 入力版、現在状態の評価、整合する状態ID、事象別の同定・比較結果、根拠、エラー、再現記録 |

患者属性と年齢属性は現実装で三つ組の値なので、独自の平均などで単一数値へ変えない。スカラーの危険要因12種と中間・総合7種を基本に、必要な事象だけを登録する。実装済みFuzzy条件は別の種類として登録する。数値の閾値・重要性条件・状態一覧の具体値は設計承認の対象であり、例示の値を採用済みとは扱わない。

### 2.2 既知情報の具体例

次は形式を示すための文書内JSONであり、実データや設定ファイルではない。KFはrawの事実に対する制約である。参照先を自由な式やファイルパスとして解釈せず、検証済みの項目名だけを許可する。

```json
{
  "schema_version": "proposal-1",
  "knowledge_version": "S02-stub-A-v1",
  "staff_id": "stub-A",
  "time_id": "t0",
  "origin": "ai_virtual_staff_stub",
  "known_facts": [
    {
      "entity_id": "P01",
      "field": "pose_features",
      "operator": "equal_vector",
      "value": [1.0, 0.0, 0.0, 0.0],
      "tolerance": 0.0
    }
  ],
  "known_relations": [
    {"relation_id": "internal_external", "tag": "not_assessed"}
  ],
  "known_risks": [
    {
      "patient_id": "P01",
      "time_id": "t0",
      "event_id": "P01.iv_proximity.high",
      "tag": "not_known"
    }
  ]
}
```

姿勢ベクトルの項目順は既存FeatureEncoderの定義に固定し、画面には意味を併記する。例の値が立上りを表すという対応は、実装時に定義と照合してから決める。患者の姿勢を一部だけ既知にする場合は、許可した成分名を指定する。

KE/KRのタグは`known`、`not_known`、`not_assessed`の三値とする。省略は`not_assessed`であり、`not_known`へ変えない。IVポール位置の制約がないことは「位置が未知」であり、「IVポールが存在しない」ではない。物体不在や既存エンジンの数値初期値も未知の代用にしない。

事実についても、収集時の原回答には三値タグを保存する。そのうち`known`と明示された有効な回答だけを、計算用の`known_facts`へ変換する。`not_known`と`not_assessed`の行は来歴には残すが、値をΩの制約へ使わない。これにより、計算上のKFは既知制約の集合のまま、明示的未把握と未評価を区別できる。

初期の仮想スタッフは、こうした入力を供給する代替用のプログラム又はファイルである。自由文からAIが独自に正解を作る構成にはしない。想定知識を明示したプロファイルを保存し、評価用の正解表は別に管理する。

### 2.3 結果の具体例

以下も架空の形式例であり、計算結果ではない。数値スコアだけでなく「何が未確定で、どの状態を見れば確認できるか」を返す。

```json
{
  "status": "ok",
  "scope": "finite_library",
  "run_id": "example-only",
  "theta_id": "theta-A",
  "theta_hash": "example-hash",
  "true_state_id": "state-01",
  "compatible_state_ids": ["state-01", "state-02"],
  "events": [
    {
      "event_id": "P01.iv_proximity.high",
      "patient_id": "P01",
      "event_type": "factor",
      "true_value": 0.8,
      "lower_truth": 0,
      "upper_truth": 1,
      "identified_from_facts": "ambiguous",
      "counterexample_state_ids": ["state-02"],
      "known_relation_tag": "not_assessed",
      "known_risk_tag": "not_known",
      "candidate_reason": ["factual_ambiguity", "provided_knowledge_gap"],
      "presentation_status": "candidate",
      "comparison": {"conditional_event_expectation": 0.5}
    }
  ]
}
```

`factual_ambiguity`はKFから確定できないという計算結果、`provided_knowledge_gap`は明示的に与えた未把握タグである。別々に記録し、後者を算法が未認識を発見した成功に数えない。KRがその患者・時刻・事象について`known`なら`already_reported_known`として再提示から外すが、計算結果は消さない。KEが`known`でも現在の成立が分かるとは限らず、KF由来の候補は消さない。

## 3. 同定処理の順序

| 順序 | 処理と出力 | 誤った解釈を防ぐ条件 |
| --- | --- | --- |
| 1 | 入力版・ID・数値・共有配置と事象定義を検証する | 任意式・任意パス・重複ID・非有限数値を受理しない |
| 2 | 一度生成したθを固定し、内容ハッシュを保存する | 個人設定を全情報条件と既知情報条件で作り直さない |
| 3 | LからKFを満たすΩ(KF)を作る | Ωが非空で、x*がLかつΩに含まれることを確認 |
| 4 | x*とΩの各状態をScenarioLoader→FeatureEncoder→RiskEngineで評価する | 同じ共有場面から患者別特徴を再生成。未知の特徴量を0にしない |
| 5 | 要因・中間・総合・実装Fuzzy条件ごとに同じ成立条件を評価する | Fuzzyの構造係数δと現在の成立条件を分け、存在しない特別増幅を足さない |
| 6 | 現在成立する重要事象について、Ω内の成立下限・上限と不成立の代替状態を求める | KE/KRタグを数理上の確定可否へ混ぜない |
| 7 | 同じ事象・Ω・知識タグで強い比較法を計算し、出力集合を照合する | 比較後に閾値や事象を変更しない |
| 8 | 計算候補、入力された認識タグ、再提示の扱い、再現記録を分けて保存・表示する | UIの件数を人の未認識の強さや事故確率と表示しない |

強い比較法の最小構成は、Ωの各状態に正の重みを与え、事象の成立値の条件付き期待値qを厳密計算する方式とする。現在成立する事象で`1−q>0`となることと、不成立の代替状態が存在することは同値である。そのため本同定案に対する同等の比較対象として実装予定に入れ、優越性を前提にしない。正の重みは有限一覧上の検証用であり、現実の発生確率と呼ばない。Conditional SHAPは別途比較する場合も同じ情報・出力条件を使い、既存の五群分解をそのままConditional SHAPと呼ばない。

## 4. モジュールと既存コードの境界

新規実装は承認後に`unrecognized_risk_poc/`内へ置く。最初はPythonの計算部分とReact/TypeScript画面だけにし、データベースやLLM接続は加えない。下表は作成予定であり、今回はREADMEと設計図以外を作らない。

| 予定先 | 責務 | 依存・禁止事項 |
| --- | --- | --- |
| `backend/contracts.py` | 入出力型、列挙値、ID・数値・版の検証 | 判定条件をUI側に重複実装しない |
| `backend/model_adapter.py` | 個人設定、場面変換、既存エンジン呼出し、Fuzzy内訳取得 | 既存modulesは読取利用。危険度の数式を改変しない |
| `backend/identify.py` | Ωの抽出、事象成立、下限・上限、根拠、KE/KRの表示分類 | 現実の認識や因果関係を推定しない |
| `backend/compare.py` | 同一入力から比較法を実行 | 正解表を読み同定結果を補正しない |
| `backend/local_api.py` | 固定JSON要求の受信、結果の受渡し | シェル起動、任意Python実行、任意ファイル参照を公開しない |
| `frontend/` | React研究者画面と後のスタッフ提示画面 | 危険評価はサーバ結果を表示。認証・チャット・Codex呼出しを流用しない |
| `data/`、`runs/` | 承認した模擬入力、実行ごとの出力と再現記録 | 実患者情報・認証情報・会話セッションを持ち込まない |

`RiskEngine.evaluate(frame)`は結果を返すので、保存はPoC側が担う。`make_personalized_risk_config`で同じ個人設定を作り、既存の`RiskConfig`がfrozenでも内部辞書は変更可能な点に注意する。評価前後のハッシュ一致を確認し、設定を変更する処理へ共有参照を渡さない。

Fuzzy内訳は既存`evaluation_study.additional_evaluation.trace_rules`の対応を調べて取得する。同モジュール全体やprivate補助関数への依存を増やす前に、公開可能な読取adapterを検討する。最小限の計算をPoC側へ写す場合は、入力順・四条件・出力が既存処理と一致することを実装後に検証する。見守り段階の条件順を配列位置だけで解釈しない。δは固定θの注記であり、状態不確定性の事象として数えない。

既存の`knowledge.json`、`config.json`、`snapshots.json`、`provenance.json`は、型と来歴の参考になる。例は`outputs/REQ004_pilot_20261018T142554/analysis-v2/weighted_sum/AI-R08/`にある。ただしsnapshotは患者別特徴であり、任意の代替共有場面を復元できるとは限らない。別の`scenes.json`もScenarioLoader形式と異なるため、無変換では取り込まない。これらの模擬結果を今回の性能検証結果に流用しない。

## 5. ファイルとReactをつなぐ方法

最初の計算確認は、固定形式のJSON入力をPythonへ渡し、JSON結果を保存する方法で行う。その後、同じ処理をローカルJSON APIから呼ぶ。二経路で計算を重複させず、APIを使わなくても同じ入力を再実行できる構成とする。

| 予定API | 入出力 |
| --- | --- |
| `GET /api/catalog` | 許可した場面・θ・仮想スタッフ・事象定義のIDと版を返す |
| `POST /api/identify` | 場面ID・現在状態ID・θ ID・知識ID・事象定義IDだけを受ける。結果IDと結果を返す |
| `GET /api/results/{run_id}` | 検証済みIDに対応する保存結果を返す。ファイルパスは受け取らない |

UIで編集した知識を使う場合も、許可された項目・演算子だけの`KnowledgeProfile`を検証してから受理する。サーバは`127.0.0.1`へ限定し、同一オリジンのReact画面から呼ぶ案とする。要求サイズ、状態数、事象数の上限と処理時間の上限を設け、無制限な状態生成を受け付けない。初期は同期処理で足りる規模に限定し、失敗時には結果の空配列だけで済ませず理由を返す。

Python標準ライブラリHTTPの小さなAPIを候補とし、フレームワーク導入は必要性を確認してから決める。既存React/TypeScript/Vite構成は画面とfetch処理の参考にできるが、既存discussion-chatbotの会話・認証・CLI実行・セッション保存とは接続しない。現環境にはNumPy等がある一方、root requirementsにはNumPyの記載がないため、承認後に専用依存一覧と実際のimportを照合する。今回はインストールも起動もしていない。

## 6. 研究者画面と実スタッフの提示画面

![研究者画面の未実装例](../unrecognized_risk_poc/design/figures/research-console-wireframe.png)

研究者画面は、左側で場面・現在状態・θ・既知情報を選び、中央で全情報条件とKFから整合する状態を確認し、下部で事象別の候補と代替状態を読む構成とする。「θは共通」「有限一覧内の判定」「認識タグは入力条件」を常に表示する。事象の詳細から、現在の場面と不成立の代替場面を並べて確認できるようにする。

計算候補と明示的未把握タグは別の欄に表示する。総合危険度の差が小さい場合も要因別の結果を閲覧でき、qによる比較結果が同値であればそのまま示す。読み込み中、入力矛盾、計算失敗、正常だが候補0件を別々に表示し、「返答なし」で混同させない。この図は画面構成の提案であり、動作するReact画面ではない。

![実スタッフの提示画面の未実装例](../unrecognized_risk_poc/design/figures/staff-view-wireframe.png)

実スタッフ評価へ移る際は、仮想スタッフの知識供給部分を、人から事前に取得したKF/KE/KRへ置き換える。計算・入出力の定義は固定し、研究者だけが全情報条件・正解表・代替状態を確認する。スタッフ用API応答は許可した表示項目だけに絞り、非表示CSSだけで全情報を隠す方法は使わない。

スタッフには提示前の回答画面と提示後の確認画面を分け、事前回答を提示後に上書きしない。未回答を`not_known`へ置き換えず、取得不能・未回答として記録する。提示文は「現在の観測からはこの危険要因が評価されます」のように、モデルの評価と根拠を示す。医療判断の正誤やスタッフの見落としを断定しない。実スタッフ評価は確定した研究方針だが、対象者・同意・課題・取得方法の具体化と実施は後続段階で行う。

## 7. エラーと再現記録

| 状態・エラー | 意味と扱い |
| --- | --- |
| `invalid_input` | 入力の必須値欠落、未知のID、範囲外、NaN等の非有限な入力、未対応版、事象参照誤り。計算せず該当項目を返す |
| `out_of_support` | x*がLにない。状態一覧を修正するまで同定を停止する |
| `inconsistent` | KFの矛盾、Ωが空、又はx*がΩ外。候補数へ換算しない |
| `model_error` | 評価失敗、モデル出力の必要値欠落・非有限値、θ変化、成立値と集合の不変条件違反。部分成功を正常結果と混ぜない |
| `boundary_unresolved` | 有限精度で閾値境界の成立・不成立を決められず、当該runは結果不完全。同じ数値判定規則を全方式に適用し、正常な候補0件・正答・臨床的な結論として扱わない |
| `ok`かつ候補0件 | 有効な入力で候補がなかった結果。人が全部理解している証拠とはしない |

境界未解決時には、該当事象ID・入力値・閾値・数値判定規則の版を保存し、画面にも「結果不完全」と表示する。決められた事象だけの部分結果を参考表示しても、run全体を`ok`へ変えない。評価集計では正常な候補0件や正答へ含めず、結果不完全の件数を別に記録する。境界例の入力で全方式が共通の状態になることも、承認後の確認項目とする。

各実行ではコードHEADと差分有無、Python/依存版、実行コマンド、設定の内容ハッシュ、場面・L・KF/KE/KR・事象定義の版とハッシュ、比較重み、開始終了時刻、エラーを記録する。乱数を使う段階だけseedと生成方法も記録する。固定一覧の厳密照合なら、乱数を使わないことを明記する。入力値は模擬データに限定し、既存provenanceから必要な来歴だけを選んで保存する。

## 8. 承認後の実装順序と確認項目

| 段階 | 作成するもの | 次段階へ進む確認 |
| --- | --- | --- |
| 0 設計の採否 | 数理・シナリオ・型・閾値・比較条件の具体版 | 本設計の修正点と実装対象を研究責任者が承認 |
| 1 計算の最小接続 | 型、模擬場面、既存モデルadapter、固定θ | 既存例と同じ値、共有場面からの特徴再生成、θハッシュ不変、未知ゼロ禁止 |
| 2 同定と比較 | Ω抽出、事象判定、反例、q比較、JSON保存 | S01〜06と負例、全事実既知で計算候補0、KE/KR三値、qとの集合同値、矛盾時の停止 |
| 3 研究者画面 | ローカルAPI、React画面、場面と根拠の閲覧 | APIとファイル実行の一致、候補0と失敗の区別、固定ID・入力上限、再現記録 |
| 4 模擬評価 | 固定条件での実行と出版用結果図 | 実験実施の承認後、設計007の指標・棄却条件で検証。模式図を実測図と混同しない |
| 5 実スタッフ評価 | 人の入力取得、スタッフ画面、事前/事後記録 | 実施条件の承認、提示前の真値漏れ防止、仮想入力との差を記録 |

通常の境界値テストに加え、座標を一つ変えると同じ物体を参照する複数患者の特徴が連動して再計算されることを確かめる。実装済みFuzzy条件とδの符号・入力順の照合も行う。これらは実装後の予定であり、本作業では未実行である。
