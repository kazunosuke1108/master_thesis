# 未認識リスク同定PoC：研究の流れと設計案

## 1. 今回の問いへの答え

既存の危険度評価を再利用し、**「現在は成立しているが、スタッフが知っている事実だけでは成立を確定できない危険内容」を、その理由とともに出す**最小PoCを設計した。未知の値をゼロで埋めず、既知事実に合う複数の状況を残して比較する。総合危険度が同じでも、IVポール近接などの内訳が違う場合を扱える設計である。

ただし、この仕組みだけでは新アルゴリズムの新規性を主張できない。同じ危険内容ごとに条件付き期待値を求める既存の考え方でも、後述の条件下で同じ候補を得られる。**単純な総合値差分では捉えられないことと、強い既存法でも解けないことは別である。** 本設計では、その強い比較も省略せず、研究を続ける判断と新手法案を見直す判断の両方ができるようにした。

数理、シナリオ、データ・処理順序、React画面、段階的な実装計画を以下の文書にまとめた。今回の成果は設計案であり、アプリの実装・研究実験・有効性の確認は行っていない。

## 2. 初見の読者に伝える研究の流れ

病棟共有空間では、スタッフは複数患者への対応や他業務と並行して見守りを行う。そのため、システムが観測した患者文脈・空間的文脈を、スタッフもすべて把握しているとは限らない。患者が立ち上がったことは知っていても、近くのIVポールまでは知らない、という違いがあり得る。

既存モデルは、行動や物体との近接などの危険要因を計算し、内的リスク・外的リスク・総合危険度へ統合する。本研究で追加したいのは、その評価そのものの作り直しではない。**システムが現在評価した危険のうち、スタッフの既知情報では何が不足するかを特定する処理**である。同じAHP重み・Fuzzyルール・モデル構成を使い、情報の違いと判断設定の違いを混ぜない。

そこで、スタッフに既知と指定した事実を満たす状況を複数用意する。「IVポールが近い状況」と「遠い状況」の両方が残るなら、スタッフの既知事実だけではIVポール近接の危険を確定できない。現在の観測が前者なら、その危険内容を提示候補とし、後者を「なぜ既知情報では確定できないか」の確認例として記録する。

この処理は、人が実際に気づいたかを読み取るものではない。関係の知識や具体的な危険内容の把握は別に指定し、未評価を未把握と決めつけない。初期PoCではAI仮想スタッフを実験条件のスタブとして用い、方式と検証条件を確認する。本評価では実際の医療スタッフに置き換え、模擬条件の正解と人の認識・臨床的な妥当性を分けて評価する。

論文の流れとしては、①把握できる情報の不足、②同一判断設定による二条件の定義、③危険要因・中間評価・実装済み条件の照合、④総合値差分では落ちる場面、⑤強い既存法との比較、⑥AIスタブでの検証と本評価への接続、の順が考えられる。新規性の節は比較結果に応じて書き換える必要があり、現時点で「既存法に勝る新算法」を結論に置かない。

## 3. 同定処理を具体的にどう作るか

### 3.1 最小の入力と出力

入力は、現在の観測、固定した判断設定、比較する状況の有限一覧、スタッフの既知情報、評価対象とする危険内容の定義である。一つの状況には、その時刻の患者・物体・スタッフの位置や姿勢を一緒に保持する。同じ座標から計算される複数の危険要因を、独立に書き換えないためである。

「事象」は、各状況で成立か不成立かを判定できる評価内容を指す。例えば「患者P01のIVポール近接リスクが、あらかじめ定めた値以上」を一件とする。この値は初期PoCの設計条件であり、医学的な危険閾値として扱わない。

出力は、患者ID・事象ID・現在の評価値・既知事実からの確定／未確定・判定を確認できる別の状況・元観測とモデルへの参照を一件にまとめたものとする。すでに把握済みと指定した危険内容は再提示対象から外す。ただし、「総合危険度を知っている」ことから「そのIVポール近接の根拠も知っている」とは推定しない。

### 3.2 具体的な処理順序

1. 全入力と判断設定の来歴を確認する。現在の観測が状況一覧に含まれ、既知情報と矛盾しないことを確かめる。
2. 既知事実に合う状況だけを残す。残らない場合は入力不整合として停止する。
3. 既存の `RiskEngine` を同じ設定で適用し、各状況の危険要因・中間評価・総合危険度を得る。
4. 事前定義した事象について、現在の成立と、残った状況での成立を判定する。
5. 現在は成立し、残った別の状況では不成立になる事象を、既知事実からは確定できない候補として記録する。
6. 関係の知識・危険内容の把握タグを別に照合し、提示候補と根拠、比較法の結果を保存する。

この保証は用意した有限一覧の中に限る。一覧に含めなかった姿勢や連続座標まで確認したことにはならない。また、すべての観測事実が既知なら、関係を理解していない人の存在をこの計算だけでは見分けられない。その場合の関係未把握は、別に与えた条件として表示する。

### 3.3 実装済みの関係だけを対象にする

Fuzzy統合の入力条件が現在成立しているかを、事象として登録する。現行の四段階の統合を対象とし、「立ち上がりとIVポールに特別な危険増幅がある」と新しく仮定しない。Fuzzy式の非加算部分を表す係数は判断設定で固定されており、それ自体を状況ごとに未知になる危険として数えない。計算上の条件依存を、現実の因果関係とも呼ばない。式とコードの対応は数理設計006に示した。

## 4. 何を検証すれば研究の判断に使えるか

### 4.1 六つの場面と仮想スタッフ

| ID | 場面 | 確かめること |
| --- | --- | --- |
| S01 | スタッフが立ち上がりを知らない | 行動の事象を、現在成立と既知事実の不足から取り出せるか |
| S02 | 立ち上がりは知るが、IVポール位置を知らない | 未知の近接要因を落とさず、専用の増幅関係は創作しないか |
| S03 | 全事実は知るが、関係を未把握と指定 | 計算で発見した不足と、外から指定した未把握を分けられるか |
| S04 | 総合値が同じでも、IVポールと車椅子の内訳が異なる | 総合値だけでは失う危険内容を、要因別に扱えるか |
| S05 | 全事実と対象内容を把握済み | 新しい未把握内容がない場合に不要な提示をしないか |
| S06 | 立ち上がり×IV専用増幅がモデルにない | 未実装の関係を発見したと報告しないか |

仮想スタッフは自由な性格描写だけで作らず、同じ判断設定の下で「どの事実・関係・危険内容を知るか」を変える条件として作る。AIには指定範囲から説明を作らせるが、同定器の答えを見て正解を作らせない。原回答・AI補完・実験用の知識条件を区別する。具体的な条件、成立表、データ分割と評価案はシナリオ・評価設計007にまとめた。

![同じ集約値でも危険要因の内訳が違う例](../unrecognized_risk_poc/design/figures/equal-total-different-factors.png)

図2：S04の手計算による説明図。IVポール・車椅子・手すりの重みを各1/3と仮定し、手すり値0.2を固定した例。前二者の値0.8と0.2を入れ替えても、外的静的リスクは両方0.4となる。ほかの入力を固定すれば後段の値も等しくなる。ただし、その配置・特徴量を現実装で作れるかは未検証であり、実験結果ではない。事象別の条件付き期待値でも同じ未確定判定を得られる点を併記した。[SVG](../unrecognized_risk_poc/design/figures/equal-total-different-factors.svg)。

### 4.2 強い比較法を入れる理由

比較する状況が有限で、残ったすべての状況に正の重みを置くとする。事象が成立する状態を1、不成立を0とした条件付き期待値は、不成立の状況が一つでもあれば1未満になる。したがって「現在は成立するが期待値は1未満」という判定は、今回の「成立しない別の状況が残る」という判定と一致する。

このため、同じ事象・状態・知識条件を渡した**事象別の条件付き期待値**を最小の強い比較にする。Conditional SHAPは、条件付き期待値に基づいて入力への寄与を分配する既存法である。総合危険度だけを出力にする場合の制約と、要因・事象ごとに適用した場合の能力を分ける。詳細と一次資料は数理設計006、シナリオ・評価設計007に記載する。

S04は、総合値差分や単一出力の寄与では失う情報があることを示すための場面になる。一方で、**強い多出力比較でも解けない場面は、今回の設計段階では見つかっていない。** この不足を埋めるために比較法への入力を減らしたり、提案側だけへ関係や知識タグを渡したりしない。

同じ候補が出ることは動作の正しさの確認になるが、同定性能の優位ではない。その場合、統合仕様、根拠の追跡、候補の整理、計算負担に別の改善があるかを検討する。改善がなければ、新算法という仮説を縮小・棄却する。研究責任者の承認なしに新たな主要評価指標へ切り替えない。

## 5. 最小PoCと画面の役割

PoCは、既存モデルを呼ぶPython側、固定したシナリオと知識条件、結果を確認するReact側からなる構成を提案する。新しい実装場所は `unrecognized_risk_poc/` とし、既存モデルは読取利用する。処理の正しさを先に確認し、その後に画面をつなぐ段階計画とする。

研究者用画面では、全情報と既知情報の二条件、残った状況、候補と根拠、比較法の結果を同時に確認する。スタッフ提示画面では、実験条件で与える情報と簡易な追加出力だけを見せる。全情報・正解・比較結果を先に見せると、知識条件の検証にならないためである。

## 6. 次に採否を判断する設計項目

以下はPMの提案であり、今回の設計着手承認だけで採用済みにはしていない。

| 提案 | 採用時の意味・残る制約 |
| --- | --- |
| 初期は有限の同時状態一覧を使う | 手で追える検算が可能。一覧外への一般化は保証しない |
| 事象の成立／不成立を共通の比較単位とする | 要因・中間評価・実装済みFuzzy条件を比較可能にする。閾値・重要性条件の具体値は別途固定が必要 |
| 既知事実と、関係・危険内容の三状態タグを分ける | 未評価を未把握と誤認しない。実人の認識自動推定は行わない |
| 事象別の厳密な条件付き期待値を強い比較に含める | 同じ候補になる可能性を正面から検証する。初期からSHAP全計算を必須にしない |
| S01〜S06と独立した期待表で検証する | 正例だけでなく、全既知・未実装関係・不整合入力を確認する |
| Python＋ローカルAPI＋Reactを専用ディレクトリに実装する | 既存モデルを再利用し、研究者画面とスタッフ提示を分ける。今回の成果は設計のみ |

次の工程は、これらの設計案の採否と、実装する範囲の承認である。θ・状態一覧・事象と閾値・重要性条件・評価指標・データ分割の確定状況を揃えてから、承認された段階の実装へ進む。
